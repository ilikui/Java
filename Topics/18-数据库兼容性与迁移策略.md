# 18｜数据库兼容性与迁移策略

> 配套练习：[Spring Boot 图书 REST API](../Practice/springboot-library-api/README.md)
> 当前基线：JDK 17、Spring Boot 3.4.4、JdbcTemplate、Flyway、H2 默认测试、PostgreSQL 16 Testcontainers 集成测试。

## 1. 先明确兼容性结论

当前项目**已针对 H2 与 PostgreSQL 建立测试路径，但尚未证明兼容 MySQL**。不要把“JDBC 能连接”或“应用能启动”当作兼容性完成。

| 维度 | H2 | PostgreSQL 16 | MySQL 8.x |
|---|---|---|---|
| 当前定位 | 默认开发与快速回归 | 已配置 Testcontainers 集成测试 | 尚未验证 |
| Flyway 迁移 | 有专用 Flyway 数据库模块 | 有专用 Flyway 数据库模块 | 需要加入驱动与 Flyway 数据库模块，并调整迁移脚本 |
| 自增主键语法 | 当前脚本可用 | 当前脚本可用 | 当前 `GENERATED BY DEFAULT AS IDENTITY` 需要适配 |
| 时间类型 | 测试语义与目标库需核对 | 支持 `TIMESTAMP WITH TIME ZONE` | 类型与时区语义不同，需明确存储约定 |
| 行锁 | H2 行为不能代替生产验证 | 已使用 `SELECT ... FOR UPDATE` 测试路径 | InnoDB 支持行锁，但必须在目标版本上验证 |
| 并发、回滚、迁移升级 | 快速回归 | 已编写对应集成测试，仍需 CI/Docker 实跑 | 尚无集成测试 |

## 2. 已知 SQL 方言差异

项目迁移脚本使用了以下结构：

- `BIGINT GENERATED BY DEFAULT AS IDENTITY`：PostgreSQL 与 H2 可用；MySQL 通常使用 `BIGINT AUTO_INCREMENT`。
- `TIMESTAMP WITH TIME ZONE`：PostgreSQL 有明确支持；MySQL 没有完全相同的列类型语义。应先决定统一存 UTC，还是采用应用层时区转换，再设计目标列类型。
- `CHECK` 约束：MySQL 版本差异需要留意，目标版本应至少明确到支持并执行 CHECK 约束的版本。
- `SELECT ... FOR UPDATE`：PostgreSQL 与 InnoDB 都支持，但事务隔离级别、索引命中、锁等待与死锁行为仍需要实测。

因此，不应直接把当前 Flyway SQL 原封不动用于 MySQL，也不应只修改 `DB_URL`。

## 3. 推荐的工程化做法

1. **先固定目标版本**：明确 MySQL 版本、字符集、排序规则、时区和事务引擎（InnoDB）。
2. **分离迁移脚本**：保留通用业务迁移的版本治理原则；如确实需要不同 DDL，使用明确的 Flyway locations（例如 `db/migration/postgresql` 与 `db/migration/mysql`），不要在已发布迁移上做破坏性修改。
3. **配置显式的数据源档位**：通过 Spring profile 或独立配置选择目标数据库；驱动、Flyway 模块和迁移目录必须一致。
4. **用真实数据库测试**：对每种声称支持的数据库运行相同的行为契约测试，而不是只跑 H2 测试。
5. **观察事务和锁**：覆盖最后一册并发借阅、库存调整、审计插入失败后的回滚、死锁/锁等待边界。
6. **验证升级而不只是全新建库**：从旧版本迁移到新版本，确认既有数据、默认值、索引、约束和审计表均正确。
7. **记录验证证据**：注明数据库精确版本、测试命令、测试报告和是否因 Docker 缺失而跳过；跳过不等于通过。

## 4. MySQL 接入前检查清单

- [ ] 添加 MySQL JDBC 驱动与对应 Flyway 数据库模块。
- [ ] 为 MySQL 建立独立的迁移目录，并验证全新数据库初始化。
- [ ] 验证主键生成与 `GeneratedKeyHolder` 的行为。
- [ ] 统一时间存储策略，测试借阅、归还与审计时间。
- [ ] 检查关键字、大小写敏感性、排序规则和唯一索引。
- [ ] 验证分页、价格过滤和动态排序白名单。
- [ ] 使用 InnoDB 实测 `SELECT ... FOR UPDATE` 与最后一册并发借阅。
- [ ] 人为制造审计写入失败，确认库存与审计在同一事务内回滚。
- [ ] 测试旧版本 schema 升级，并确认旧数据保留。
- [ ] 在 CI 中启动目标 MySQL 容器并确保集成测试没有被跳过。

## 5. 面试自测

1. 为什么 H2 测试全部通过，仍然不能证明 PostgreSQL 或 MySQL 兼容？
2. Flyway 为什么不应该修改已发布的迁移脚本？
3. `SELECT ... FOR UPDATE` 为什么必须与事务边界、索引和隔离级别一起考虑？
4. 数据库迁移如何做到可重复部署、可追踪、可验证？
5. 如何区分“测试跳过”“测试执行通过”和“测试未配置”？

**完成标准：**至少在目标数据库容器中执行完整迁移、CRUD、并发借阅、事务回滚与升级测试，并保存可复查的测试报告。未运行的数据库不能标记为已兼容。
